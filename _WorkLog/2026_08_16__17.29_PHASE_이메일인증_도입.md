## DB 실측 결과 (service_role 키로 REST 직접 조회, 2026-08-16)

- `profiles` 실제 컬럼: `id, name, phone, interests, member_type, message, role, created_at, updated_at, email, current_job, notes`
- `profiles.interests` = **TEXT[] (배열)**
- `profiles.email` — **UNIQUE 제약 없음**
- `profiles.id` — **auth.users FK 없음** (임의 UUID 삽입이 201로 성공)
- `w2center@naver.com` → profiles에 1건(id `27ee097a…`, notes `예비 멤버`), **auth.users에는 없음** (auth 총 179명)
- `notes ILIKE '%예비 멤버%'` = **93건**

## ✅ 해결한 근본 버그 — interests 타입 불일치 (치명)

`profiles.interests` 는 TEXT[] 인데 코드는 **문자열**을 보내고 있었다.
```
PATCH {"interests":"AI test"} → HTTP 400  22P02 malformed array literal: "AI test"
PATCH {"interests":""}        → HTTP 400  22P02 malformed array literal: ""
PATCH {"interests":[]}        → HTTP 204  ✅
```
빈 문자열조차 거부되므로 **interests 가 포함된 모든 프로필 저장이 항상 실패**했다.
가입 완성 저장·프로필 수정 전 경로가 해당. 재시도 루프가 5회 실패 후 조용히 넘어가며 이를 은폐.

**수정**: `waatNormalizeProfileUpdates()` 공용 헬퍼 추가 (`supabase-config.js`),
`DB.updateProfile` 양쪽 판본(`supabase-config.js`, `db.js`)에서 저장 직전 문자열→배열 정규화.
- 단위 테스트 8/8 통과 (빈문자열·공백·쉼표구분·후행쉼표·기존배열·null·키부재·원본불변성)
- 실 DB 검증: 정규화 payload → HTTP 204, 값 정상 반영, 원복 완료
