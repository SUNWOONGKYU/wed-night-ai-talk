### 발단 — "인증메일이 오지 않음"
원인은 **이메일 오타**였다. PO가 모바일에서 `w2cente**t**@naver.com`(끝 t)으로 입력.

## 🚨 사고 기록 — config push 로 운영 auth 설정 초기화 (2026-08-16 08:5x, 복구 완료)

**무슨 일**: 최소 `config.toml`(project_id + `[auth] enable_confirmations`)로 `supabase config push` 실행.
`--yes` 없이도 **확인 프롬프트 없이 즉시 적용**됐고, config.toml 에 없는 항목이 CLI 기본값으로 덮어써졌다.

| 항목 | 원래값 | 덮어써진 값 |
|---|---|---|
| `site_url` | `https://waat.community` | `http://127.0.0.1:3000` |
| `additional_redirect_urls` | 운영 5개 | `["https://127.0.0.1:3000"]` |
| `mfa.totp.enroll/verify` | true | false |
| `email.max_frequency` | 1m0s | 1s |
| `email.otp_length` | 8 | 6 |

게다가 `enable_confirmations` 를 `[auth]` 아래 뒀는데 실제 키는 `[auth.email]` 이라 **목표도 달성 못 했다.**

**영향**: 이 상태에서 Google OAuth 로그인·비밀번호 재설정 링크가 127.0.0.1 로 향했을 것. 노출 시간 약 1~2분.

**복구**: 위 diff 의 remote 측 값을 그대로 `config.toml` 에 명시하고 재푸시 → 전부 원복 + `[auth.email] enable_confirmations = true` 적용.

**재발 방지**: `config.toml` 을 저장소에 커밋(`2299df4`)해 운영값을 고정. 파일 상단에 경고 주석.

**교훈**: `supabase config push` 는 diff 를 보여주지만 **묻지 않고 적용한다.** 부분 설정 파일로 실행하면 안 된다.

## ✅ 해결한 근본 버그 — interests 타입 불일치 (치명)

`profiles.interests` 는 TEXT[] 인데 코드는 **문자열**을 보내고 있었다.
```
PATCH {"interests":"AI test"} → HTTP 400  22P02 malformed array literal: "AI test"
PATCH {"interests":""}        → HTTP 400  22P02 malformed array literal: ""
PATCH {"interests":[]}        → HTTP 204  ✅
```
빈 문자열조차 거부되므로 **interests 가 포함된 모든 프로필 저장이 항상 실패**했다.
가입 완성 저장·프로필 수정 전 경로가 해당. 재시도 루프가 5회 실패 후 조용히 넘어가며 이를 은폐.

**수정**: `waatNormalizeProfileUpdates()` 공용 헬퍼 추가 (`supabase-config.js`),
`DB.updateProfile` 양쪽 판본(`supabase-config.js`, `db.js`)에서 저장 직전 문자열→배열 정규화.
- 단위 테스트 8/8 통과 (빈문자열·공백·쉼표구분·후행쉼표·기존배열·null·키부재·원본불변성)
- 실 DB 검증: 정규화 payload → HTTP 204, 값 정상 반영, 원복 완료
