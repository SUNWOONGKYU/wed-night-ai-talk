- **Phase 5 가 가장 위험** — 틀리면 PO 가 관리자 페이지에 못 들어간다.

  · `is_admin()` 은 SECURITY DEFINER 라 함수 안에서는 컬럼 권한이 적용되지 않는다.
    (정책에 `EXISTS(... profiles.role ...)` 를 직접 인라인하면 깨진다 — 오늘 실측으로 확인했다)

- **Phase 2 한계** — 파일명을 바꿔도 git 히스토리의 옛 파일명은 남는다.
  본문 실명은 히스토리에도 없다(처음부터 마스킹된 채 커밋됨). PO 에게 이 한계를 알렸다.
- **Phase 3 주의** — 이미 적용된 마이그레이션 파일을 폴더 밖으로 옮기지 않는다.
  `supabase db push` 가 참조하므로 물리적 이동은 위험하다. 문서화로 처리한다.
- **Phase 6** — `style-src 'unsafe-inline'` 은 유지한다. `style="..."` 속성이 사이트 전반에 쓰여
  제거하려면 CSS 전면 개편이 필요하고, script-src 만큼 위험하지도 않다.

## 추가 전수 감사 (2026-09-02 저녁, PO "남기는 거 하나도 없이")

REST 로 테이블 전수 실측 + 정책·권한 메타데이터 감사를 돌렸다.

**새로 발견해 조치한 것**
- `post_views` 1197행이 익명에게 열려 있었다. viewer_id(회원 UUID) + 열람시각이
  들어 있어, 게시판 표시용으로 열어둔 profiles(id,name) 과 조인하면
  "누가 어떤 글을 언제 읽었는지" 전체 이력이 복원됐다.
  원인은 드리프트가 아니라 저장소의 `"post_views readable by all" USING(true)` 정책.
  클라이언트는 이 테이블을 읽지 않는다(조회수는 posts.view_count) → 완전 차단.
- `inquiries` / `email_logs` / `guest_attendance` — RLS 는 막고 있었지만 익명 컬럼
  권한이 남아 있었다. 두 번째 벽으로 회수(authenticated 는 관리자 화면이 쓰므로 유지).
- `delete_user(uuid)` — 프로덕션에만 있고 저장소에 없던 함수(대시보드 드리프트).
  가드는 정상이었으나 profiles.role 을 직접 봐 단일화 경로를 안 탔다.
  원본 정의를 그대로 가져와 저장소에 등재하고 is_admin() 으로 맞췄다.

**확인만 하고 조치 불필요**

- anon 실행 가능 함수의 가드 전수 확인 — 관리자 함수는 실호출로 42501 거부 확인.
